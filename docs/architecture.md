# Architecture

React fetches Flask arrivals and alerts together on station selection, manual Refresh, and automatically 30 seconds after the previous refresh completes. Polling lives in `frontend/src/hooks/useStationData.js`. One “Last refreshed” timestamp records the browser's completion time only after both responses succeed and pass frontend validation, including empty responses. It advances on manual and automatic refresh even if the feed contents or backend `updated_at` are unchanged. Before the first successful refresh it reads “Not yet refreshed”; selecting another station starts fresh. While loading or if either request fails (including timeout or invalid responses), the previous timestamp remains. The affected panel shows an error and retains its last successful data; the other panel may still update. A later fully successful refresh advances the timestamp and clears errors.

The displayed timestamp uses the browser's clock and local time zone; it describes frontend fetch completion, not MTA feed freshness. Backend `updated_at` remains unchanged as the feed timestamp used for freshness checks. Flask returns normalized JSON and caches responses with a configurable TTL.

The MTA integration boundary is services/mta_client.py, connected through transit_service.py at application initialization. Demo mode uses four development stations. Live mode loads the generated catalog once, then uses the adapter for arrivals/alerts. A CachedFeedSession caches only validated responses by upstream URL for 30 seconds by default, coalescing concurrent calls within a process. The adapter revalidates freshness on each use and normalizes current predictions. Failures return 503 without substituting demo data. Timeout and freshness thresholds are configurable. Frontend live/demo labels follow health `transit_mode` and response `source` values. See the [MTA data reference](mta-data.md) for sources, field mappings, and catalog maintenance.

Flask routes validate HTTP input; services own business logic. Transit responses stay in the process-local cache rather than Firestore. For multiple workers or replicas, use a shared cache and a coordinated feed fetcher to avoid repeated upstream requests. Local startup uses the Flask development server; the hosted backend runs Gunicorn as described in [deployment](deployment.md).

Firebase Auth runs in React. React sends an ID token in Authorization: Bearer. Flask verifies the token (including revocation), derives uid, and accesses only that user's Firestore favorites. Frontend SDK does not access Firestore directly; rules deny client database access. The Admin SDK bypasses these rules, so route authorization is required.

Persistent schema: users/{uid}/favorites/{station_id} with station_id:string. Future preferences can live in a dedicated user document. Use station IDs consistently across frontend, API, and data imports.
